# 演示数据

独立版离线页面(`build-offline.mjs` 生成的单文件 HTML)用的数据,2026-11-19 录入。

**工单是编的,研判结果是用我的研判引擎算出来的。** 政诉工单里有投诉人的个人信息,真实工单一条都不进仓库和离线页面;
这里的 562 条是照真实数据的样子编的脱敏样例,再用我写的研判服务在本机对它们跑一遍,得到候选、优先级、复发、
对标案例等结果。页面顶部也写着"演示数据是编的样例,不是真实工单"。

## 样例工单怎么编的

- **字段**:和本机客户端上传给平台的脱敏信封一样(`gov-risk-cases/v1`:映射编号、渠道、创建/关单时间、状态、处理结果、
  平台与模板风险等级、业务线、部门类型、城市、问题分类、场站编码、投诉人键、四段正文)。
- **正文**:用固定的句式模板加随机数字(度数、金额、时长、日期)拼出来,按投诉类型分了几十种说法。
  地点、人名、电话、订单号这些在真实链路里会被本机脱敏掉的内容,直接写成脱敏后的占位:`[地点]`、`[人名]`、`[手机号]`、
  `[长编号]`、`[部门]`。没有任何真实的姓名、电话、地址、证件号、车牌。
- **编号**:映射编号 `GT-…`、场站编码 `ST-…`、投诉人键 `U-…` 都是对 `demo-…` 字符串取 sha256 得到的短码,
  和任何真实工单、场站、手机号无关(真实链路里这些是本机密钥对真实数据算的,映射表只在本机)。
- **数量级和分布**:照我在说明文档里写过的汇总口径——约 560 条政诉,2026-05-14 起;度数/电量偏高约 5%、每月 5–7 条、
  几乎都"问题已解决"、平台定级几乎全是 L5。其余分布按业务常识设定:

| 项 | 分布 |
|---|---|
| 条数 | 562:政诉 556,舆情 6(手工录入的舆情事件,部门类型"媒体") |
| 时间 | 2026-05-14 至 2026-11-18;按月 38 / 88 / 97 / 102 / 95 / 91 / 51(5 月从 14 日起,11 月到 18 日) |
| 业务线 | 充电 534,加油 28 |
| 部门类型 | 市场监管 267,12345热线 150,其他 48,消协 32,媒体 14,交通运输 13,税务 11,未知 10,网信 8,个人信息保护 6,公安 3 |
| 现象(引擎判的) | 占位费或停车费争议 75,金额偏高 68,无法启动或中途断电 60,退款/余额 56,价格标示不一致 50,优惠会员 50,发票 39,电量偏高 33,场站管理 26,车辆受损 23,客服推诿 22,账号 20,无法拔枪 16,其他 15,出现他人数据 9 |
| 状态 | 已处理 530,处理中 21,待处理 5(未结的集中在最近两周),舆情 6 条无状态 |
| 平台定级 | L5 539,L4 13,L3 4;模板风险等级 L5 250、L4 135、L3 89、L2 31、L1 8、空 49 |
| 场站 | 309 条带场站编码,涉及 132 个场站、35 个城市;32 个投诉人投诉过两次以上 |

- **埋进去的几处"系统性"模式**(引擎事先不知道,看它能不能找出来):度数偏高每月都有,其中 9 条集中在同一场站,
  同一场站还有 4 条"出现他人数据";一个场站的停车费减免争议 10 条;一个场站反复无法启动 7 条;
  一个场站线上线下价格不一致 6 条。
- **对标案例库**(3 个,也是编的):前两个照说明文档里写的两个真实教训概括(度数过高引发舆情、设备流水号重复导致串单),
  第三个是编的(停车费减免规则告知不清)。

## 研判结果怎么来的

用 `services/guardian-backend/src/gov-risk/` 里我写的研判服务 `GovRiskService`,配内存存储(和 `test/gov-risk.spec.ts` 同一做法),
按本机客户端的方式分两批上传,平台收齐后自动研判,再读出结果。录入时间 2026-11-19 18:16(北京时间)。

本机没有配模型密钥,所以逐条研判走的是引擎里的规则兜底、候选复核没有跑,结果包的"方法说明"如实写着"未用模型";
这和原平台没配模型时一样:候选卡上"可能机理"一栏是空的(看"鉴别线索"指向哪些机理),下钻的工单下面没有逐条研判那一行
(规则兜底的逐条结论平台不落库),"研判方式"里"超出单次额度 562 条"也是引擎在没配模型时的原样输出。

结果:候选 45 个(现象级 15、同一场站 30;高优先 21、中 14、低 10),排第一的是"电量/度数偏高"(100 分,关单后仍在出现,
像已知案例 2 个),同一场站的度数偏高(9 条)与出现他人数据(4 条)都进了高优先。

## 文件

| 文件 | 内容 |
|---|---|
| `result.json` | 页面接口 `GET /api/gov-risk/package` 的返回:结果包(`gov-risk/v2`)、研判运行、数据集信息 |
| `cases.json` | `GET /api/gov-risk/cases` 能读到的全部 562 条脱敏工单(页面下钻用),新的在前 |
| `feedback.json` | `GET /api/gov-risk/feedback` 的初始状态:空的,不带任何人的跟进和备注 |

所有者用的是演示账号,数据里不出现任何人的账号名;离线页面里改跟进状态、写备注、重新研判都只在页面内存里生效。

## 个人信息核对

- 上传时平台那道个人信息扫描(`gov-risk.validate.ts`:手机号、打码手机号、证件号、车牌、8 位以上长编号、邮箱、链接)整批放行;
- 再用本机客户端脱敏用的那套样式(另含座机、10 位以上字母数字编号、"××先生/女士"、"姓名:××"、"××充电站/小区/街道/路××号"等)
  逐条扫正文和对标案例:零命中;
- 正文去掉数字和开头语("消费者反映,"之类)后是 139 种句子,逐条看过,没有人名、电话、地址、车牌,占位只有 `[地点]`、`[人名]`、`[手机号]`、`[部门]`、`[长编号]` 五种;
- `portal/tests/gov-risk-workbench.test.cjs` 里有一项每次都会再扫一遍。
