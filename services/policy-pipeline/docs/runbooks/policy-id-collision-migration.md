# policy_id 撞车:修复口径与存量迁移

对应修复:`fix/l1-policy-id-collision`。
本文只讲**存量数据怎么办**——代码修复本身不动任何已有文件,两件事必须分开做。

## 1. 缺陷与生产实测

2026-09-07 对生产 vault(`/root/policy-vault/0_raw/policies/`,1653 篇)全量扫描:
**21 个 policy_id 各挂 2~10 份文件,共涉及 59 份。**

三层缺陷叠加,前两层制造碰撞,第三层让碰撞静默落盘:

| 层 | 位置 | 缺陷 |
|---|---|---|
| RC-1 | `metadata_extractor.extract_official_number` | 取正文里**第一个**文号形状的串,不检验它是否属于本件。政府页正文常引用上位文件、常把相关链接拼进正文 |
| RC-2 | `ingester.compute_pid` | 只截文号**尾数**(`(\d+)\s*号`),丢掉文种前缀与括号年 |
| RC-3 | `ingester.ingest_one` | 只对**文件名**查重(`__1`/`__2`),对 **id 不做任何唯一性保证**;SCHEMA §2 写明的「碰撞:加 `_a` `_b` 后缀」从未实现 |

证据:
- 10 份 2026 年江苏成品油公告(第7~16号)全被打上 `发改电〔2015〕10号`——那是正文引用的 2015 年调价机制文件。全部落到 `P_2026_JS_FGW_10`。
- `发改能源〔2026〕884号` 同时挂在「7月31日国内成品油价格调整」与「新型能源体系建设"十五五"规划」上;`979号` 同理。
- 有一篇的 `official_number` 是 `根据财库〔2022〕3号`——正则的 `[一-龥]{2,8}` 贪婪前缀把「根据」吃了进去,直接坐实这是引用而非本件文号。
- 全库 **70 篇**文号括号年与发文年相差 ≥2 年(同年 518 篇、差 1 年 59 篇),是同一类污染的规模信号。其中 3 篇文号年份反而**晚于**发文年,属同类反常。
- 21 组碰撞里 **20 组是不同 URL 的不同文档**(必须分号),仅 1 组是同 URL 重复入库(必须复用原号)。

## 2. 代码修复做了什么(已在本分支)

- **RC-3(核心)**:新增 `ingester.PidRegistry`,按 SCHEMA §2 发 `_a`/`_b`/…/`_z`/`_aa` 后缀。身份 = 归一 URL(复用 `dedup.normalize_url`):号空着就用,同一份文档拿回原号(**重跑幂等**),别的文档占了就顺延。`step5_ingest` 全批共用一张表。
- **RC-1**:`extract_official_number` 增加两条排除——剥掉被贪婪前缀吞进来的引用动词;文号括号年与发文年相差 ≥2 年时跳过该匹配(跨年发文差 1 属正常,不误杀;调用方不给 `date` 时该规则不生效)。
- **RC-2:不改**。SCHEMA §2 明确定义尾号取「文号尾号」并**已经预见**碰撞、给了后缀规则。改尾号格式会重写全部 1653 个 id,收益只是好看,代价是全下游重挂——不值。RC-3 到位后 RC-2 的碰撞已能被正确分号。

把生产 1653 篇按新逻辑重放:**碰撞组 21 → 1**,37 篇改号,1616 篇 id 原样不动。
剩下那 1 组是同 URL 的同一份文档被入库两次(`P_2026_HL_FGW_a770e0cb`)——同 URL 发同一个号正是发号器该有的行为,那是 **dedup 漏网**,另案。

## 3. 关键口径:id 一次发放,此后冻结

**`id` 不是当前元数据的纯函数,而是首次入库时发放、之后不再重算的稳定标识。**
`PidRegistry` 用 URL 身份把这条变成了运行时事实(同 URL 永远拿回同一个号)。

由此推出两条硬约束:

1. **RC-1 的存量回填绝不可顺带重算 id。** 那 70 篇文号错的政策,回填只改 `official_number`(改成空或正确值),**`id` 原地不动**。否则 `compute_pid` 读到新的 `official_number` 会把它们全部改号,把一次小修变成全库迁移。
2. **代码上线本身不改任何存量文件。** 上线后新采的文档立刻拿到唯一 id;37 篇存量坏号在单独的整改动作里处理。两件事不要合并成一次操作。

## 4. 存量整改(单独动作,需 handoff 给 Codex 执行)

### 4.1 盘子(2026-09-07 实测)

21 组撞号、涉及 59 份文件,拆成三堆,**三堆的处置完全不同**:

| | 篇数 | 处置 |
|---|---|---|
| 保留裸号 | 21 | 下游派生当前就指着它,id 不动 |
| 真·不同文档 | 30 | 分号(`_a`/`_b`)+ **补跑 L2 派生** |
| 真·重复件 | 8 | 走 dedup 合并/归档,**不分号** |

### 4.2 谁留裸号:可机械判定,不用人工猜

`_meta/business_view/{pid}.yaml` 里有 **`sanitized_from`** 字段,直接记着该派生是从哪个 raw 文件抽的
——这就是「下游实际指向谁」的权威记录。21 组里 **20 组唯一命中**;仅 `P_2026_GS_FGW_74` 没有
business_view,回落取 `fetched_at` 最早的一份。

让 `sanitized_from` 指向的那份保留裸号,则该组的 business_view **一个字都不用改**,churn 最小。

### 4.3 关键:这 30 篇在派生层里**根本不存在**

它们的 pid 一直被同组另一份占着,所以从来没有属于自己的 business_view
——连带 relations / analysis_context / heng-pg 里也都没有它们的行。

**所以迁移不是「改个名」,是让 30 篇此前隐形的政策首次进入派生层**,拿到新号后要补跑 L2
派生。这有 LLM 成本,是本次整改真正的工作量所在,排期要按这个估,不能按「改 38 个字符串」估。

(全库 1653 篇政策 vs 1573 份 business_view,缺口 80;这 30 篇是其中可解释的一部分,
剩下 50 篇的缺口是另一件事。)

### 4.4 那 8 篇重复件不能顺手分号

`【政策】` / `【规范性文件查询】` / `【商品价格】` 是同一份文件走了不同渠道栏目,标题只差一个方括号前缀;
还有同 URL 被入库两次的。**给它们发 `_a` 会在派生层凭空造出重复政策**,比现在撞号更难查。
这 8 篇走 dedup 合并或归档 `_duplicates/`,不进发号流程。

### 4.5 旧号不能凭空消失

改号的那几份,**把旧 id 写进 `aliases`**(SCHEMA §2 已有该字段,`dup_aliases` 亦可),
否则 Obsidian 既有反链与外部引用会全断。

### 4.6 影响面

改一个 id 会牵动所有按 id 关联的派生,必须同一个事务内一起改:

| 消费方 | 形态 |
|---|---|
| vault raw | `0_raw/policies/*.md` frontmatter 的 `id` 与 `aliases` |
| business_view | `_meta/business_view/{pid}.yaml` —— **pid 是文件名**,改号即改名 |
| relations | `from` / `to` 两端 |
| analysis_context | `policy_id` 字段 |
| heng-pg 投影 | `scripts/sync/pg_writer.py` 写出的行 |
| Obsidian | 正文 wikilink / 反链 |

### 4.7 执行顺序

1. 生成 remap 表(按 4.2 判定裸号归属、按 4.4 摘出重复件),人工过一遍分类结果;
2. **dry-run**,打出全下游变更集(vault / business_view 改名 / relations 两端 / analysis_context / pg 行数);
3. 变更集确认后一次性 apply,记 `state/last_run.json`;
4. 补跑 30 篇的 L2 派生;
5. 复跑 `scripts/audit/dump_status.py` + 全库 id 唯一性扫描,确认碰撞归零;
6. heng-pg 投影重跑对账。

生产 vault 只读红线不变:整改属生产写,按 server-ops 规矩由用户亲手执行。

## 5. 顺带确认的另案(本次不改)

- **dedup 漏网**:同 URL 的同一份文档能被入库两次(`P_2026_HL_FGW_a770e0cb`)。`DedupIndex` 已有 URL 维度,为何没拦下需单独查。
- **月刊侧兜底可退役**:`l3_monthly/shortlist.py` 的 `id_collision` 标记 + slate `title_hint` 消歧是下游补丁。等 4.4 整改完成、碰撞归零后可以撤,但**在那之前必须留着**。
