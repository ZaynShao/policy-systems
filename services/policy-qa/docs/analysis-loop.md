# 从"平铺工具循环"到"分阶段分析"

现在的问答是一条**平铺的 tool-calling 循环**:模型拿到问题,自己决定调什么工具,
调够了就作答。没有规划阶段,没有核验阶段。

这份文档记录为什么要改、改成什么、以及每一步的依据。**不是照搬开源架构**——
下面每条改动都对应一个在生产或评测里实测到的毛病。

## 现在的毛病(都有实据)

| # | 毛病 | 证据 |
|---|---|---|
| 1 | **盲目并发扫描**。prompt 让它"盘点式问题至少扫四轮",但它不知道该扫什么,于是一口气并发发七八个检索 | 2026-08-18 生产日志:一个问题 8 次检索,其中 3 次是挨个猜部委名;并发打爆连接池 |
| 2 | **靠 prompt 自律保证事实**。逐字抄文号、不推算附件数字,全是 system prompt 里的规矩,没有任何一步去核对 | 真模型冒烟时写出过 `浙发改价格〔2026〕21号`,而库里是〔2024〕21号(被废止旧件的号) |
| 3 | **读原文吃掉预算**。先读几篇就没次数补扫了 | 评测:预算 12 时补扫被饿死,只好把上限提到 18 并在 prompt 里调顺序——治标 |
| 4 | **关系与评论只能按 pid 查**,无法用于发现 | `build_relations_sql` / `build_commentary_sql` 的入参都只有 pid |
| 5 | **跨条线文件既没主题也没高分**,只能靠穷举机关名捞 | 主题评测:golden 14 篇里 5 篇无主题,且集中在财税/认证类;那 1 篇只靠机关扫描才捞到的正是车船税 |

第 1、3 条同源:**没有"先想清楚要查什么"这一步**,所以只能用广度换覆盖。

## 参考的成熟做法

- **Anthropic《Building Effective Agents》** 的六种工作流:prompt chaining、routing、
  parallelization、orchestrator-workers、evaluator-optimizer、autonomous agent。
- **GPT Researcher**(27k stars)的 planner-executor-publisher:规划器把问题拆成子问题,
  执行器并行检索,发布器综合成带引用的报告。它的关键取舍是**用并行换同步**,
  但前提是先有规划——并行的是"已知要查什么"的子任务,不是盲目撒网。

这两条合起来正好治第 1 条毛病:我们现在做的是**没有规划的并行**,
拿到了并行的成本,没拿到并行的收益。

## 目标形态

```
问题
 │
 ├─[0] 路由      简单问题(解读某一篇)直接走旧的平铺循环,不付规划成本
 │
 ├─[1] 规划      一次**不带工具**的模型调用,输出结构化检索计划:
 │               扫哪些主题 / 哪些业务线 / 时间窗 / 哪些机关兜底
 │               输入里注入主题登记表(13 条)与业务线口径,让它有的可选
 │
 ├─[2] 取证      按计划执行检索。并发受连接池闸门约束,不再是模型即兴发挥
 │
 ├─[3] 精读      按计划的判据挑 N 篇读原文
 │
 ├─[4] 综合      出初稿
 │
 └─[5] 核验      拿"已读原文"逐条比对初稿里的文号/日期/数字/引文,
                 列出无据可依的断言 → 修订或标注
```

对应关系:[1]+[2] 是 orchestrator-workers,[0] 是 routing,[5] 是 evaluator-optimizer,
[1]→[2]→[3]→[4] 是 prompt chaining。

## 为什么这样切,而不是照抄 GPT Researcher

GPT Researcher 面向开放网络,子问题之间彼此独立,所以它可以纯并行。
**我们的检索维度是相互重叠的**——同一篇政策会同时被"主题=充电"和"业务线=充电"捞到。
所以规划阶段的价值不在拆分,在**选维度**:决定这个问题该用主题、业务线、机关还是关系图,
以及为什么。选对一个维度胜过盲扫四个。

第 5 步也和它不同。GPT Researcher 的发布器是"综合成报告";我们要的是**事实核验**——
月刊那套纪律是事实零容错,而模型已经证明它会在文号上编造。核验器要做的不是润色,
是拿初稿里的每个具体数值回去和已读原文对峙。

## 分期

**一期(已做):** 只加规划阶段。规划结果作为"检索计划"注入 system prompt,
下游仍是现在的平铺循环。这样能立刻验证"有计划的检索是否比盲扫省"且可回滚
(`POLICY_QA_ENABLE_PLANNER=0`)。衡量指标:同一批 golden 问题下的检索次数与召回。

一期实现里有两个**必须先踩过才知道**的点:

- **计划与 prompt 不能各说各话。** 原本是把计划附在原 system prompt 后面,结果计划里
  没给机关扫描,模型仍然扫了财政部/税务总局/市场监管总局三轮——因为 prompt 里硬写着
  "必须主动补扫……至少扫财政部、税务总局"。两处指令打架时模型跟更硬的那条走,
  规划变成只加成本不减检索(18 次撞上限)。所以补扫教条抽成 `SWEEP_DOCTRINE`,
  有计划时整段换成 `PLAN_SUPERSEDES_SWEEP`。**判断权只能归一处。**
- **精读要单独设闸。** 总预算是一个池子时,读原文会把它吃光(实测读掉 11 篇、
  总调用 20 次)。而额度用尽时要**指路而不只是拒绝**——检索结果里带着
  `impact_snippet`,回答影响用它就够,不必每篇都读两万字。

**二期(已做):** 核验阶段,`app/verifier.py`。

实现时改了设计:原本打算照 evaluator-optimizer 再叫一次模型审初稿,动手时发现
**搞错了性质**——"文号必须逐字照抄""引用原文必须逐字"本来就是字面规则,
那么正确的检查就是字面比对。让另一个模型去 judge,既贵又引入新的幻觉面。
最终是零成本、确定性的:正则抽出文号与引文,回本轮工具返回过的材料里做子串查找。

两个刻意的取舍:

- **证据取"本轮工具返回的全部内容",不只是读过的原文。** 检索列表里的文号模型
  也见得到,据此转写不算编造。判据是"模型见没见过",不是"这个号属不属于本件"
  ——后者是语义判断,交给 prompt 规则和用户核对。
- **不改写答案,只报告。** 答案是流式吐出去的,回头改写做不到;而且把存疑处标出来
  让用户点引用核对,比服务端偷偷改字更符合这套纪律。

用户的问题也算进证据——用户自己给的文号被复述回去不算编造(答案评测里抓到过
这个假阳性)。

**三期:** 路由与关系图发现。前者省钱,后者补第 4 条毛病。

## 规划自语:四层防线

模型会把思考过程写进答复。这条纪律**光靠 prompt 管不住**,实测按顺序失败了两次,
所以最终是四层叠加:

| 层 | 机制 | 挡得住什么 | 实测 |
|---|---|---|---|
| 1 | prompt 写"不要输出思考过程" | 一部分 | 单独用会漏 |
| 2 | 本轮出现工具调用 → `delta_reset` | 中间轮次的自语 | 有效,但最后一轮没有工具调用,挡不住 |
| 3 | `===答复===` 分隔标记,标记前的不发 | 模型**愿意用标记**时的自语 | 两次跑一次用了一次没用 |
| 4 | 开头自语的确定性过滤 | 前三层的漏网 | 零命中 |

第 4 层刻意做成**高精度低召回的白名单模式**,而不是"自称词 + 流程词"的组合判据。
组合判据会误伤「我建议重点关注第三条,原文材料显示……」这类正经论述——它有自称
也有流程词,却是答复本身。**漏删一句只是难看,误删正文是事故**,而且用户不会知道
自己少看了什么。所以 `tests/test_chatter_filter.py` 里反向用例比正向用例多。

第 3 层的实现有个必须守住的点:**攒着不发是有上界的**。攒够 `HOLD_MAX_CHARS`
(400 字)还没等到标记,就当这轮它不用标记,把攒下的原样放出去——否则首字延迟无界。
三个释放点(标记命中 / 攒够上限 / 轮末残留)都要保证"一个字都不能少"。

## 关系图与评论信号:量过了,不建

原计划把关系图和评论信号从"按 pid 查"扩成"用于发现"(比如"最近有哪些新政废止了
旧规")。**2026-08-18 实测数据后放弃**——不是不想做,是没有数据支撑。

关系图(全库 1440 篇,611 篇有关系,1909 条出向边):

| 关系类型 | 边数 | 对"发现"的价值 |
|---|---|---|
| references | 697 | 太泛,查出来是噪声 |
| aligns_with | 618 | 同上 |
| cites_basis | 285 | 按 pid 查已够用 |
| clarifies | 165 | 同上 |
| derives_from | 109 | 同上 |
| **extends** | **15** | 有价值但太稀 |
| **iterates** | **13** | 同上 |
| **supersedes** | **7** | 同上 |

真正适合做发现的三类(supersedes/iterates/extends)合计 35 条,占 1.8%;
**近 90 天窗口里一条都没有**。做出来的工具会稳定返回空结果,
而空结果会被模型读成"最近没有政策废止旧规",比没有这个工具更糟。

评论信号:188 条,只关联 90 篇政策(**覆盖 6%**)。`signalRole` 分布尚可
(risk 127 / opportunity 50 / execution 11),但 `businessTag` **61% 为空**,
充电只有 4 条。按业务线反查评论同样会常态返回空。

**什么时候该重新考虑:** 关系抽取覆盖率上去(尤其 supersedes 这类强关系),
或评论信号的 businessTag 补全到七成以上。那是 pipeline 侧的事。

## 不做的

- **不引入 LangGraph / LlamaIndex 之类的编排框架。** 这里的状态机只有五个节点、
  一条主路径,用框架换来的是一层抽象和一个新依赖,不划算。Pydantic AI 已经提供
  了工具循环与结构化输出,规划和核验用它的 `output_type` 就能做。
- **不做多轮反思循环(reflect → retry → reflect)。** 每一轮都是真金白银的 token,
  而评测显示当前的失败不是"想得不够深",是"查得不对"。先把查对了再谈想深。
